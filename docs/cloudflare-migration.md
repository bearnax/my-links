# Cloudflare publishing migration

Status: proposed direction for the links site, 23 November 2026. The existing
GitHub Pages site remains the production site until a replacement has been
tested and cut over. This document is a handoff, not evidence that the
Cloudflare project, credentials, or migration already exist.

## Goal

Give Will one easy-to-edit Airtable base for the links directory and, later,
a personal landing page and portfolio. Content edits should be published by a
deliberate action without a routine GitHub pull request. Keep the public site
fast, accessible, responsive, and usable without client-side JavaScript.

## Proposed architecture

- Airtable is the content source. Inspect the actual base before changing its
  schema. Reuse shared project records across sites where appropriate.
- Eleventy reads and validates Airtable data at build time and generates
  static HTML. Airtable credentials remain in build secrets and never reach
  the browser or generated output.
- Cloudflare Pages builds and hosts the site. GitHub stores code. Content
  publication is manually triggered, initially using a deploy hook or a
  private shortcut. Treat the hook URL as a secret. A protected publishing UI
  is an optional future enhancement, not a prerequisite.
- R2 hosts public images. Airtable stores stable public image URLs. Existing
  R2 bucket, hostname, cache policy, and access settings need verification.
- A failed publication must not replace the last successful deployment. Make
  publication status and actionable validation errors easy to find, and
  document rollback and a content export/backup approach.

The landing page is future work. Design the content boundary so it can share
projects and visual tokens with the links site, without requiring its content
model or a second site to be built as part of this migration.

## Current system and known issue

The current site builds from committed `data/links.json`, generated by
`scripts/sync-links.py` using IDs in `data/airtable-schema.json`. GitHub
Actions currently builds/deploys to GitHub Pages and manages the Airtable sync
through a PR. Preserve the current public site and existing Airtable data
while testing a replacement.

The most recent inspected manual sync (21 November) reached Airtable but
reported that `Image URL` was missing from the Items table. Some other runs
were queued and the owner reported cancellation errors. Treat those as
observations at that time, not a complete diagnosis or a reason to modify live
data. The deployed JSON observed previously did not include the new featured
project metadata. Verify current state before migration.

## Migration work

1. Check the current repository, open PRs, and production deployment. Inspect
   the Airtable metadata and representative records read-only. Identify the
   actual image field and types, field IDs, favorite behavior, projects,
   sections, URLs, images, and anything currently used by the live page.
   Do not invent field IDs or assume records have been migrated.
2. Map the real base to the content model. Keep existing records and their
   links. Plan any Airtable schema changes and confirm them with Will before
   making changes to his base. Keep favorites in their normal section and also
   display them in Favorites when checked, with a transition for the legacy
   Favorites section.
3. Implement one build-time ingestion path with deterministic normalized
   data, pagination, validation, useful errors, optional-field handling, and
   tests. Handle unavailable Airtable or incomplete data by failing the build
   clearly. Never embed tokens or temporary credentials in the build.
4. Preserve existing site behavior and visual direction: tactile, colorful,
   clearly tappable links, responsive light/dark modes, search, accordions,
   favorite shortcuts, and optional featured-project descriptions and images.
   Confirm actual imagery loads and link counts avoid counting duplicate
   favorite appearances. Maintain accessibility and a useful no-JavaScript
   page. Keep the personal-site design related but do not build it here.
5. Set up a non-production Cloudflare preview and manual publish path. Test
   with real content and safe fixtures, including missing fields, invalid
   URLs, duplicate favorites, edited and deleted records, no-op publication,
   image URLs, and failure without replacing the previous deployment. Verify
   desktop and phone widths, both themes, keyboard navigation, and search.
6. Confirm publishing status, accurate last-published date, rollback, backup,
   secrets, and a practical owner runbook. Review resulting content and design
   with Will. Only then arrange the production cutover, custom domain/DNS,
   and retirement of obsolete GitHub Actions. Verify the live deployment and
   keep a documented rollback to the old site.

## Open decisions

- Confirm the actual Airtable schema and decide whether and when to separate
  projects from ordinary links. Keep per-site visibility and presentation
  separate from project classification.
- Confirm the production hostnames, existing Cloudflare account/project,
  R2 public image domain, and the links site's eventual relationship to the
  personal site.
- Verify Cloudflare Pages Git integration, deploy-hook behavior, build logs,
  project limits, and secret configuration against the account before choosing
  the exact publish shortcut. Decide whether publication needs a private
  Cloudflare Access page later.
- Confirm whether Will wants a preview before every content publish or is
  happy to publish directly with a rollback option.
- Agree on backup destination and frequency, and on the meaning of counts and
  the displayed update date.

## Access needed for implementation

Read-only Airtable access scoped to the Links CMS base requires a token with
`data.records:read` and `schema.bases:read`. Do not paste secrets into chat or
commit them. Cloudflare setup requires appropriate account/project access;
the exact scope depends on the chosen hosting and trigger setup. Verify access
before promising a cutover.
